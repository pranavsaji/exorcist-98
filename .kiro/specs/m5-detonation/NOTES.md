# Notes: m5-detonation (built by Claude Code)

Decisions where the spec left room, and the one thing not done.

- **Client.** The existing `BedrockClient` sends one prompt and gets text back, with no tools. The chamber needs tool use, so `BedrockClientImpl` gained `converse()` (same SDK, same lazy loading, same `modelIdFor('haiku')` inference-profile config) behind a new `ChamberClient` interface in `types.ts`. Tests use `FakeChamberClient` (`llm/__tests__/fake-chamber.ts`).
- **Turns.** "At most 2 turns" means at most 2 model calls. For the `file` and `tool-result` placements, the conversation starts with the read already made: a pre-written assistant `read_file` / `fetch_issue` call, with the fenced suspect text as its result. Both model calls then go to the model's own behaviour.
- **Fencing.** The suspect text is placed only as data: a tool result, or the description of one extra tool, `project_helper`. It goes inside `<<<NAME_START_nonce>>> … <<<NAME_END_nonce>>>` with a fresh nonce for each detonation, and any copy of the nonce in the text is removed. The system prompt depends on the nonce alone; a property test checks this. The system prompt does not tell the model to ignore instructions in the data, because the chamber measures what the text can make an ordinary agent try. The attacker-chosen file name is not placed in the task either; only an allow-listed extension is kept (`docs/NOTES.<ext>`).
- **Placement tools.** Besides the four fake tools, `tool-description` adds `project_helper` (it carries the suspect description) and `tool-result` adds `fetch_issue` (the seeded call). Both are fake.
- **Verdict, wider than the spec in two places.** First, a planted secret in the arguments of *any* tool counts, not only `http_post`/`send_message`: passing `.env` to a poisoned tool is how tool poisoning steals data. Second, `run_shell` that dumps the environment, touches a secret path or writes to shell startup files / `authorized_keys` also counts. An outbound call that carries no secret stays `inert`, as the spec says, but the transcript still shows it.
- **Inconclusive.** A third verdict. It covers a failed call, an answer that fails the zod check, an answer cut off at `max_tokens` or with an unknown stop reason, and a model still calling tools when the 2 turns run out. It is never reported as clean, and `exorcist detonate` exits 3 for it.
- **Secrets.** Six fake credentials with realistic shapes, random for each detonation, inside fake `.env`, `~/.aws/credentials`, an SSH key, `~/.npmrc` and the environment. They are found in any shape (reusing the canary matcher) and masked as `[SECRET NAME]` in every transcript, finding and report.
- **EX-024.** `match.analysis: detonation` (new enum value; the signature engine skips analysis rules). It is reported as a `heuristic`-source finding on the file's worst existing finding, and the attempted calls are the rationale.
- **Not done: real-Bedrock evaluation.** The owner's AWS login session (profile `exorcist-98`) had expired on 2026-11-23, and the credential provider refused the first call locally, so 0 model calls were billed. `docs/DETONATION.md` says so. Run `scripts/detonation-eval.ts` after `aws login` to get real results.
- **Known gap (documented in DETONATION.md).** `scan --detonate` only detonates files that already have a medium-or-worse or AI finding, as the spec says. The reworded attacks in the evidence set have none, so reaching them needs `--ai` or `exorcist detonate <file>`.
